# ObsidianCore Sync 0.2.0 — Warifu対応リリースノート

**承認済み版：内部版 `0.2.0`、RCタグ `v0.2.0-rc.1`、予定GAタグ `v0.2.0`。** RC配布物の生成・端末受入・GA公開が完了したことを示すものではありません。対象はObsidianクライアントです。Warifu v0.3.1は別途導入するNextcloudアプリで、クライアントに同梱するものではありません。

### 何が変わるか

新規設定では「Warifu（Files）」が既定になり、自動同期はOFFです。通常のMarkdownと添付ファイルをNextcloud Filesに置いたまま、標準WebDAVで同期します。この方式に独立DAVサーバー、HaRP、Bridgeは不要です。対象はWarifu v0.3.1、Nextcloud 35.0.3、64-bit PHP 8.5.12、通常の非暗号化ローカルホームです。外部ストレージやサブマウントは対象外です。

Warifu方式は応答の `X-Nextcloud-Gateway: experimental-1` とファイル内容由来のETagを検査します。適用を確認できない場合は停止し、通常DAVには戻りません。古いETagによる更新・削除が `412` で拒否された場合は再読込・競合処理へ進みます。外部サービスが条件を付けずに行う上書きまで防ぐものではありません。

### 既存利用者の更新・切替・復帰

- **今の接続を使い続ける場合：** 保存済みのWebDAV／Bridge設定は切り替わりません。転送方式の項目がない旧設定も従来のWebDAVとして読み込みます。プラグインIDは `vaultsync` のままです。更新は自動同期を止め、プラグインを無効化して、同じ端末の `.obsidian/plugins/vaultsync/` の `main.js`・`manifest.json`・`styles.css` だけを入れ替えます。`data.json`・`private/`・リモート履歴は削除しません。既存Bridgeの再導入も不要です。
- **Warifuへ切り替える場合：** 全端末と外部サービスの書き込みを止め、未解決の競合・途中処理を確認します。解決できない場合は切り替えません。Vaultの両側、端末ごとの設定と状態、旧配布物を独立バックアップから復元できることを先に確認します。管理者が[Warifuを導入](https://github.com/upiscium/Warifu/blob/v0.3.1/docs/install-nextcloud.md)し、[対象フォルダーへの適用](https://github.com/upiscium/Warifu/blob/v0.3.1/docs/check-server.md)を確認します。まずテスト用コピーで「Warifu（Files）」に専用HTTPSフォルダーURL（例：`https://cloud.example/remote.php/dav/files/alice/ObsidianVault/`）、同じユーザーID、端末別アプリパスワードを設定し、接続検査と手動同期を行います。旧方式の同期基準・競合・途中処理を流用せず、ファイルや履歴の自動移行もしません。
- **旧版へ戻す場合：** 全書き込みを止め、切替後に変更されたファイルを両側から別に保全します。旧プラグイン3点と当該端末の整合した旧設定・状態を復元し、元の接続方式・接続先を確認します。他端末の `private/` を複製したり、Warifuを無効化しただけの接続先を通常DAVとして使ったりしません。復帰でサーバーの更新は巻き戻らないため、差分を確認してからテスト用コピーで手動同期を再開します。

### 検証状況

この文書では、現在のRC候補について実施済みのテスト件数や成功結果を主張しません。ソース試験や過去の候補の結果を、今回配布するRCの受入結果として転記しないでください。

### RC配布物で確認する項目（未実施から開始）

受入記録にはRCタグ、対象commit、`release-manifest.json` のSHA-256、試験したOS／Obsidian版、各項目の結果を残します。資格情報、Vault本文、privateログは添付しません。

| テスト用Vaultで行う操作 | 合格条件 |
| --- | --- |
| 配布したRCの3ファイルを取得して新規導入 | 3点のハッシュが記録と一致し、Obsidianで起動。既定はWarifu、自動同期OFF。 |
| 旧WebDAV設定（方式項目なしを含む）と旧Bridge設定を個別に更新 | 接続方式・接続先・既存の同期状態を維持し、Warifuに自動切替しない。 |
| 通常DAVとWarifu適用済み専用フォルダーでそれぞれ接続検査 | 前者はユーザーファイルを変えず拒否。後者は条件付き更新検査を通過し、手動同期できる。 |
| 2端末で同じMarkdownを競合編集し、解決前に外部から再編集 | 古い解決結果で上書きせず、両方の変更を確認できる。履歴から別名復元し、本文も照合できる。 |
| RCで編集したあと旧版・旧設定へ復帰 | 切替後の編集を失わず、元の接続先で想定した手動同期ができる。 |

未実施・失敗項目を合格として扱いません。GAに進めるかはRC実物の受入記録と[配布物の同一性照合](release-preparation.md)で判断し、修正した場合は新しいRCとして検証し直します。

# 過去のリリース：ObsidianCore Sync v0.1.1

同期ステータスを改善したクライアント0.1.1の通常Releaseです。作者は**upiscium**、独自クライアントとNextcloud Bridgeは**AGPL-3.0-or-later**です。ObsidianCoreへの実行時依存はなく、Obsidian公式製品でもありません。GitHubのみで配布し、公式Community Pluginsには登録しません。

## 今回の変更

- 右下のステータスバーに`同期中 12/100 ファイル`のような確認済み／対象件数を表示します。無変更や削除確認も含む対象パスの確認数であり、転送成功件数ではありません。対象一覧が揃う前は`同期中（対象確認中）`、履歴整理中は件数を保持して別表示にします。
- 自動同期に失敗した場合、既存のNotifyに加えて`自動同期失敗`を表示します。再試行中も`前回自動同期失敗`を残し、エラー・中断・スキップ・編集保留のない手動または自動同期が履歴整理まで完了したら解除します。設定保存の反映・アンロード／再起動でもリセットします。
- 過去の自動同期エラー記録は別管理で、正常な再試行後も保持します。エラー記録の消去や接続確認だけでは失敗表示を解除しません。競合は別に件数表示し、保留・中断だけで新しい失敗扱いにはしません。
- 表示用の進捗通知が失敗しても同期処理は継続します。ファイル名・URL・エラー原文はステータスに出さず、永続状態・比較更新（CAS）・認証・ロック・サーバーAPIは変更しません。
- `fast-xml-parser`を5.12.0へ更新し、低重大度の[GHSA-474x-hrwr-fgx4](https://github.com/advisories/GHSA-474x-hrwr-fgx4)に対応しました。上流が示す発生条件は非既定の`stopNodes`設定で、本プロジェクトのXML解析では設定していませんが、修正版を取り込みます。必要な経由依存`is-unsafe`のみ2.0.3へ更新し、他の依存は維持しています。

## 更新・導入

1. 復元可能な独立バックアップと、小規模なテスト用Vaultを用意します。
2. 更新時は自動同期をOFFにしてプラグインを無効化し、このリリースの`main.js`、`manifest.json`、`styles.css`だけを各端末の`.obsidian/plugins/vaultsync/`へ配置します。
3. Obsidianを再起動して有効化し、手動同期・競合解決を確認してから自動同期を検討してください。

旧表示名VaultSyncからの更新でも、内部IDは`vaultsync`のままです。`data.json`、`private/`、同期履歴、Vaultデータは削除・初期化・他端末から複製しません。旧ローカル試用版も0.1.0を使っていたため、manifest版番号だけでなく配布物のSHA-256で識別してください。

**Bridgeは0.1.0から変更していません。既に導入済みならサーバー側の再導入・設定変更は不要です。** 新規にBridgeを使う場合だけ、`vaultsync_bridge-0.1.0.zip`内のREADMEを先に確認してください。実行用フォルダーは`vaultsync_bridge/`、9個のPHP/XMLとLICENSE／NOTICE／READMEを含みます。対応ソースZIP内のテスト用補助アプリを本番サーバーへ配置しないでください。

## 対応ソースとハッシュ

**対応ソースは、このリリースのAssetsにある`ObsidianCore-Sync-source-0.1.1.zip`から追加料金なしで取得できます。** 独自ソース・build config・lockfile・導入／再ビルド／検証手順を含みます。未改変npm依存はlockfileの正確なURLとintegrityで取得するため、完全オフラインのソースkitではありません。

`LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.txt`を同梱し、プラグインの`main.js`末尾にもAGPL全文と組み込んだMITライブラリ9件の通知を保持しています。再配布時も通知と対応ソースへの案内を保持してください。

`release-manifest.json`に各assetのサイズ・SHA-256と、ソースblobを照合したGitコミットを記録しています。隔離した新規依存インストールからの再ビルドとbundleの一致も配布候補作成時に確認します。manifestの`published: false`は生成時点でのローカル候補の状態です。現在の公開状況はGitHubリリースページが示します。SHA-256はファイルの同一性確認であり、発行者認証用の署名ではありません。

## 制限と検証範囲

- **通常WebDAV方式は、確認済みのNextcloud 34.0.1／34.0.5／35.0.2のETag再利用問題を安全に扱えません。** 検査を迂回せず、対応範囲内のBridgeだけを検討してください。
- Bridgeは**Nextcloud 34.0.1の通常・非暗号化の本人ホーム**に限定します。外部ストレージ、共有、他版、多数サーバー構成の対応保証はありません。対応のためのダウングレードやセキュリティ更新の保留は推奨しません。
- ステータス変更は隔離Nextcloud 34.0.1／MariaDB 12.3.2・DBロックで確認しました。XML依存更新後の最終ビルドは、同じNextcloud版のSQLite・DBロックとLinux Obsidian 1.13.7でBridge 23項目、同期18項目、GUI 15項目を通過しています。
- 依存更新後のMariaDB再試験は、Dockerのアドレスプール枯渇によりセットアップで停止し未完了です。既存ネットワークの削除・構成変更や安全ガードの緩和はしていません。MariaDB 12.3.2はNextcloud 34の公式要件一覧にないため、以前のfixture成功も上流の対応表明・本番保証とは扱わないでください。
- 今回版のWindows／Android実機、WAN、長期運用、大規模な実Vaultは未検証です。モバイル模擬試験は実機試験の代わりではありません。
- Bridgeは1ファイル25MiBまで。通信・履歴・メモリの上限と、平文の端末内認証情報・サーバー上の通常ファイルという前提をREADMEで確認してください。E2EEではありません。
- AGPLの条件に従って再配布・改変でき、法令上認められる範囲で無保証です。ネットワーク経由で利用される改変版については第13条も確認してください。
