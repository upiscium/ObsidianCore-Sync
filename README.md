# ObsidianCore Sync

ObsidianCore Sync（旧表示名VaultSync）は、ObsidianのVaultをWebDAV経由で同期する独立したプラグインです。ObsidianCoreとブランド名を揃えていますが、ObsidianCoreへの実行時依存はありません。Obsidian公式製品ではありません。Windows・Linux・Androidを対象に、通常のMarkdown／添付ファイルをWebDAVの専用フォルダと同期する構成です。

配布はGitHubのみを対象とし、公式Community Pluginsディレクトリへの申請は予定していません。リポジトリは[`upiscium/ObsidianCore-Sync`](https://github.com/upiscium/ObsidianCore-Sync)、配布物と公開状況は[GitHub Releases](https://github.com/upiscium/ObsidianCore-Sync/releases)を確認してください。ソースをローカルでビルドしただけではリリースは公開されません。

作者は**upiscium**、独自クライアント・Bridge・ビルド／テストコード・文書のライセンスは**AGPL-3.0-or-later**です。クライアントの内部バージョンは`0.1.1`、GitHubタグ名は`v0.1.1`です。Bridgeは`0.1.0`のまま変更せず、この更新によるサーバーの再導入は不要です。第三者コードには元のライセンスと著作権表示を保持します。[LICENSE](LICENSE)、[NOTICE](NOTICE)、[第三者通知](THIRD_PARTY_NOTICES.txt)を参照してください。

このプログラムはAGPLの条件に従って再配布・改変でき、法令上認められる範囲で無保証です。`main.js`末尾にもAGPL全文・プロジェクト通知・実際にbundleされた第三者ライブラリの通知全文を含めるため、Obsidianに必要な3ファイルだけを配置する場合にも表示を保持できます。設定画面にもライセンスと対応ソースの案内があります。Nextcloud本体やObsidianのライセンスは変更しません。

### 表示名と安定した識別子

今回の名称対応は、クライアント旧表示名`VaultSync`から新表示名`ObsidianCore Sync`への表示上の変更準備です。技術IDや既存データはこの表示対応に追随して改名せず、状態ファイルの移行も行いません。

| 項目 | 表示／値 | 扱い |
| --- | --- | --- |
| プラグイン表示名 | `ObsidianCore Sync` | UIと公開文書で使うブランド名 |
| ObsidianプラグインID | `vaultsync` | 安定したID。変更しません |
| インストール先 | `.obsidian/plugins/vaultsync/` | 既存のパスを維持します |
| コマンド | 表示ラベルは`ObsidianCore Sync: ...`、コマンドIDは`vaultsync:...` | 表示ラベルと技術IDを区別します |
| 設定・端末状態 | `data.json`、`private/`、既存の設定キー | 形式・場所を維持し、移行・削除しません |
| リモート履歴 | `.vaultsync/history/` | 既存の保存先を維持します |
| Nextcloud Bridge | アプリID `vaultsync_bridge` と既存APIルート | 変更しません。サーバー表示は`VaultSync Bridge/0.1.0`のままです |
| ルートnpmパッケージ | `obsidian-vaultsync` | 非公開の内部ビルド識別子として維持し、プラグイン表示名とは区別します |

表示名だけを変える準備であり、状態ファイルの移行はありません。プラグインフォルダーや技術IDを改名したり、`data.json`、`private/`、設定、履歴を削除したりしないでください。

**重要：通常のWebDAV方式では、Nextcloud 34.0.1／34.0.5／35.0.2のローカルストレージで確認したETag再利用の問題を安全に扱えません。** 検査が一度通っても問題がない保証にはなりません。この問題を検査の緩和で回避せず、**34.0.1向けには追加アプリを使う「Nextcloud Bridge（実験版）」を実装しました。**

Nextcloud Bridgeは通常・非暗号化ホーム領域で、同時要求と意図的な割り込みを実通信検証しています。前段階の検証にはMariaDB `12.3.2-noble`を使うDBロック／Redisロックの両構成とLinux版Obsidian 1.13.7の記録があります。今回のステータス表示変更では、DBロック構成の実通信／Linux GUI検証を行っています。MariaDB 12.3.2はNextcloud 34の公式要件に記載された版ではなく、ローカルfixtureの成功は上流の対応表明や本番保証ではありません。SQLiteおよびApache 2.4.69 + `FileETag Digest`にも前段階の記録があります。今回の更新のWindows／Android実機検証やownCloud検証は行っていません。ユーザーからの従来版Linux↔Androidの動作報告も、今回の更新の実機検証とは区別します。独立したバックアップとテスト用Vaultを用意してください。自動同期は初期状態でOFFです。

## 実装済みの機能

- ファイルの追加・更新・削除を双方向同期。外部WebDAVアプリによる通常ファイルの変更も比較対象にします。
- 共通の基準版を保持するMarkdownの3-wayマージ。通常の非空行のマージ規則は従来どおりです。基準版が改行コードだけの空行列の場合はEOF論理行も数え、両側が基準の行数と各行のLF／CRLF／CR配置を維持するとき、異なる空行位置への入力を位置ごとに統合します。同じ行への異なる入力は競合です。両側に変更があり、どちらかの行数／改行配置が基準と異なる場合はファイル全体の競合にします。片側だけの変更や完全に同じ変更はそのまま採用します。反復する同一テキスト全般の編集意図を解決する機能ではありません。
- 競合一覧、基準／ローカル／サーバーの比較、競合箇所ごとの採用、結果の手動編集、版の選択、両版を別名で残す操作。
- 競合画面の後から発生した変更を再検証。競合・途中の処理記録はアプリ再起動をまたいで保持します。
- 表示中の定期同期、復帰時同期、手動同期。設定画面の「同期間隔（終了後の待ち時間・秒）」は既定30秒、1秒〜30日です。設定した間隔は前回の処理完了後に待つ時間です。たとえば15秒設定で処理に約11.6秒かかった場合、次の開始は前回開始から約26.6秒後であり、固定30秒のレート制限ではありません。長い処理の重複実行や復帰時のまとめ実行を避けます。
- ファイル・フォルダ・globパターンによる端末別の除外。除外の追加自体では既存ファイルを削除しません。
- `.obsidian`内の選択したJSON／CSS設定ファイルの同期。設定の競合は自動マージしません。
- ローカルとWebDAVの復元履歴、他端末のリモート履歴の読み取り、別名ファイルへの復元。
- 強いETagによる条件付き作成・更新・削除。初回の同期処理は、サーバーが条件を実際に守るかの検査を通るまでユーザーファイルを変更しません。
- デスクトップではシンボリックリンク／ジャンクション、Vault外への解決、検出できる別デバイス境界を拒否します。
- 「自動同期エラーを確認」から、直近1件の自動同期エラー記録を端末内メモリだけで確認できます。未保存エディターによる保留だけでは自動同期エラーにせず、既存の実エラー記録も置き換えません。記録は共有用の診断JSONとは別で、ファイル保存・自動送信・クリップボードへの書き出しはしません。

Gitコマンド、Cloudflare、別の調整サーバーは不要です。Nextcloud Bridge方式だけはNextcloud側への追加アプリ配置が必要です。リアルタイム共同編集、E2EE、ユーザーごとの権限管理は含みません。

### 右下の同期ステータス（0.1.1以降）

ステータスバーを表示できる環境では、同期中に`同期中 12/100 ファイル`のように確認済み／対象件数を表示します。これは転送に成功したファイル数ではなく、両側の一覧と追跡状態を合わせ、除外ルールを適用した同期対象パスの確認件数です。無変更、削除の確認、既存の競合、サイズ超過、編集保留、エラーとなった対象も、実際に確認を試みたら数えます。履歴用のファイルや除外対象は含めません。対象一覧が揃う前は`同期中（対象確認中）`、その後の履歴整理中は件数を保持して`履歴整理中 100/100 ファイル`と表示します。件数が総数に達しても、全ファイルの同期成功や履歴整理完了を意味しません。

自動同期に実エラーがあれば、既存の通知に加えて`自動同期失敗`を表示します。再試行中は件数とともに`前回自動同期失敗`を残し、接続確認・履歴の閲覧・過去のエラー記録の消去だけでは解除しません。手動または自動同期が、履歴整理を含めてエラー・中断・スキップ・編集保留なく完了したときに解除します。競合そのものは失敗扱いにせず、従来の競合件数で別に表示します。設定保存が反映されたときとアンロード／再起動でもリセットします。保留や中断だけで新しい失敗表示にはしません。

表示は端末内のメモリだけで管理し、ファイル名・接続先・エラー原文を含みません。過去の自動同期エラー記録は別管理のため、失敗表示が消えた後も保持されます。公開済み`v0.1.0`の配布物にはこの機能は含まれません。`v0.1.1`の配布状況はGitHub Releasesで確認してください。

## Nextcloud 34.0.1向けの接続

1. [追加アプリの導入手順](nextcloud/vaultsync_bridge/README.md)に従い、`custom_apps/vaultsync_bridge`へ配置して有効化します。WebのAdmin権限に加え、ファイル配置と`occ`の実行手段が必要です。
2. ユーザーごとに既存の専用フォルダを`allowed_roots`へ登録し、実験機能を明示的に有効にします。コアのファイルロックは無効にしないでください。
3. Obsidian側で「Nextcloud Bridge（実験版）」を選び、**NextcloudのベースURL**、**Vaultパス**、ユーザー名・端末別アプリパスワードを設定します。
4. 設定を保存して接続確認し、テストVaultで手動同期・競合解決を確認してから定期同期を有効にします。

保存内容は通常ファイルのままですが、Bridgeモードの一覧・取得・条件付き変更には専用OCS APIを使用します。通常のWebDAVは外部アプリの閲覧・編集手段として残り、その変更も読み取ります。ただし、別アプリがBridgeのコミット完了後に無条件で上書きする行為までは防ぎません。

BridgeはWebDAV接続と別の同期状態を使い、旧ETagキャッシュを流用しません。古い状態・競合・履歴を自動移行・削除しないため、未解決の競合や途中処理がある状態で切り替えず、保全したテスト用のコピーから確認してください。

## ビルド

Node.js 24とnpmを推奨します。スマートフォン側にNode.jsは不要です。

```sh
npm ci
npm test
npm run build
npm run smoke:mobile
npm audit
```

Nix環境の場合、各コマンドは次の形で実行できます。

```sh
nix shell nixpkgs#nodejs_24 --command npm ci
nix shell nixpkgs#nodejs_24 --command npm test
nix shell nixpkgs#nodejs_24 --command npm run build
```

`npm run build`はTypeScriptの型検査後、ルートに`main.js`と開発用source mapを生成します。通常の開発には`npm run dev`も使用できます。依存関係は`package-lock.json`で固定しています。同じesbuild実行のmetafileから出力へ寄与したパッケージを調べ、版・ライセンス・通知全文を確認してからbundleを書き出します。不明な依存や通知の不一致はビルドエラーです。依存更新時は`scripts/bundle-notices.mjs`の検証方針と`THIRD_PARTY_NOTICES.txt`も再確認してください。

### ローカル実機テスト用パッケージ

公開リリースではない、Windows／Androidの使い捨てVaultで試すためのZIPを作成できます。作成側はLinux・Node.js 24・npm・`unzip`とnpmレジストリへの接続を使用します。使用端末側にNode.jsは不要です。

```sh
nix shell nixpkgs#nodejs_24 --command npm test
nix shell nixpkgs#nodejs_24 nixpkgs#unzip --command node scripts/package-test.mjs --build
```

`--build`なしでは説明だけを表示します。指定時は通常のビルドに加え、明示したソースだけを新しい隔離ディレクトリへ複製し、`npm ci --ignore-scripts`で依存を取得して再ビルドします。両方の`main.js`が完全一致しなければ配布物を生成しません。`dist/obsidian-core-sync-local-test-<一意なID>/`へZIPと`package-result.json`を新規作成します。ZIP名と内部トップフォルダー名は`ObsidianCore-Sync-local-test-0.1.1`です（ZIP名には`.zip`を付けます）。内部版`0.1.1`は公開済みという意味ではありません。`dist`内の既存パッケージや隔離ビルド領域は削除・上書きしません。作成中は信頼できる作業ディレクトリを他プロセスで変更しないでください。symlinkや別ファイルシステムを拒否する検査はありますが、同じユーザー権限の悪意ある同時差し替えを原子的に防ぐものではありません。

ZIPにはプラグイン3ファイル、Bridge実行ファイル9個とLICENSE／NOTICE／README、プロジェクトのLICENSE／NOTICE／第三者通知、[導入・停止・復旧ガイド](docs/device-test-guide.md)、[Windows／Android試験票](docs/device-test-checklist.md)、対応ソースZIP、サイズ／SHA-256を記録するmanifestを含めます。作成後、ZIPの全エントリー・ファイル属性・展開bytesを再検査します。`.integration/`、認証情報、`data.json`、`private/`、source map、node_modulesは含めません。ソースZIPには検証用コードを含みますが、Bridge実行用フォルダーにテスト補助アプリは混入させません。ハッシュは同一性確認であり、発行者の認証や実機での成功を証明しません。

## インストール

1. テスト用Vaultを用意します。本番データの同期コピーではなく、別途復元できるバックアップも作成してください。
2. Vault内に`.obsidian/plugins/vaultsync/`を作成します。ブランド変更準備後も、安定したプラグインIDとインストール先は`vaultsync`のままです。
3. 次の3ファイルをそのフォルダに配置します。
   - `main.js`（ビルド生成物）
   - `manifest.json`
   - `styles.css`
4. Obsidianを再起動し、コミュニティプラグインの一覧でObsidianCore Syncを有効にします。
5. Androidも同じ3ファイルをVaultの同じ場所へ配置します。隠しフォルダを表示できるファイル操作手段が必要です。

カスタム設定フォルダを使用している場合は`.obsidian`をそのフォルダ名に置き換えます。プラグイン本体・認証情報・内部状態は本プラグイン自身では同期しないため、各端末で導入・設定してください。

## 初期設定

### WebDAV

互換性を検証したWebDAVサーバーに、**このVault専用の既存フォルダ**を作成し、そのURLを指定します。アカウント全体のルートを指定しないでください。次はNextcloudのURL形式の例にすぎず、現在のNextcloud対応を保証するものではありません（冒頭の既知の問題を参照）：

```text
https://cloud.example.org/remote.php/dav/files/USERNAME/ObsidianVault/
```

URLはサービスのWebDAV設定から取得してください。ownCloudなどは構成によりパスが異なります。ObsidianCore Syncは指定したルートを自動作成しません。

- HTTPS必須。自己署名証明書の検証回避は実装していません。
- Basic認証対応。通常のアカウントパスワードではなく、用途を限定した**アプリパスワード**を推奨します。
- 認証情報をURLに埋め込まないでください。ユーザー名とパスワードは別の入力欄を使用します。
- 認証情報は端末内の`data.json`に**暗号化せず保存**します。本プラグインの同期対象外ですが、端末・他プラグイン・別の同期ソフト・端末バックアップからは読める可能性があります。
- サーバー上のノート・履歴は通常ファイルです。HTTPSは通信を保護するものであり、サーバー管理者から内容を隠すE2EEではありません。
- LAN/VPN内のサーバーは、各端末が直接接続できれば使用できます。
- リダイレクトが不要な最終WebDAV URLを使用し、信頼できるサーバーだけを設定してください。Obsidianの`requestUrl`ではリダイレクトの最終URLや認証転送の制御を十分確認できません。

設定を保存後、「接続・安全性を確認」から検査し、手動同期の結果を確認してから自動同期をONにしてください。検査は`.vaultsync/`内にランダムな検査用データを作成・更新・削除します。通常の同期も、各実行コンテキストの初回に同じ検査を自動で行います。

条件付き更新に対応しないサーバーに対する「安全性検査を無視して続行」はありません。検査用の空フォルダが残るサーバーがありますが、ユーザーデータの同期対象にはなりません。

### 除外と設定ファイル

除外欄は1行1ルールです。Vault相対パスで指定します。

```text
Private/
attachments/large-video.mp4
**/*.tmp
**/.DS_Store
```

ルールは大文字・小文字を区別し、隠しファイルにも適用します。通常のパスは同名ファイルとその配下を除外します。`!pattern`や否定extglobなどの再包含ルールは初版では非対応です。

`.obsidian`は原則除外し、設定ファイルの許可欄で**完全なファイルパス**を選択します。例：

```text
.obsidian/app.json
.obsidian/appearance.json
.obsidian/hotkeys.json
.obsidian/snippets/custom.css
```

`.git`、`.trash`、`.vaultsync`、ワークスペースJSON、プラグイン配下は選択できません。初版では他のプラグインの`data.json`も許可しません（秘密情報や端末固有設定の混入防止）。設定変更の反映にはObsidianの再起動が必要な場合があります。

## 競合・削除・復元

- 初回に同名・内容違いのファイルがあれば、共通の基準版がないため自動上書きせず競合にします。
- 通常の削除は他端末へ反映しますが、「削除と編集」が競合した場合は確認を求めます。ローカルの削除にはObsidianのローカルゴミ箱を使用します。
- 画像などのバイナリ、JSON/CSS設定、共通基準のないファイルは無理に自動マージしません。
- 自動マージの競合マーカーは解決画面にだけ表示し、通常のノート本文に自動では書き込みません。
- 「両方を残す」は、元のパスにローカル版、別名の`.remote-<id>`ファイルにサーバー版を保持します。
- 競合画面を開いた後にファイルが変わっていた場合は、解決結果で上書きせず競合を更新します。画面を開き直してください。
- メインの未保存エディター保護ガードが明示的に発した`TypedEditorDeferredError`だけを編集保留として扱います。そのファイルを未読込・不存在・削除済みとはみなしません。他のファイルの同期は続けます。手動結果の「保留（編集中）」セクション、ステータスバーの「前回保留 N」で表示します。これは最後の試行の件数であり、現在も保留が残っていること／解消したことを保証するライブ表示ではありません。
- 保留は「リモートには何も変更されなかった」という証明ではありません。リモート確定後に保留となった場合はローカル状態を未確定として記録し、保護対象の履歴を保持します。次の新しい同期でリモートを再確認し、必要なら競合として扱います。その他のI/O・CAS・ネットワーク・復旧エラーは通常のエラーです。
- 復元は別の未使用ファイル名へ行い、現在のファイルには直接上書きしません。復元ファイルは次回の同期対象です。

通常履歴は既定で**30日以内かつ1GiB以内**です。先に達した制限を適用し、日数・容量は変更可能です。ローカルは端末ごとの履歴、リモートは専用履歴領域全体のデータ量で判断します。

**基準版・未解決競合・途中処理の復旧データは通常履歴の整理対象外**です。このため1GiBはプラグイン全体の使用容量の上限ではありません。ローカルには同期対象の基準版を保持するため、対象Vaultに近い追加容量が必要になる場合があります。履歴の上限が1ファイルより小さいと保護処理を停止するため、履歴上限を増やしてください。

内部状態は接続先URL・アカウント別に`<config>/plugins/vaultsync/private/`へ保存します。接続先を切り替えても旧状態を自動削除しません。復元用のリモートデータは`<WebDAV root>/.vaultsync/history/`です。これらのファイルを手動編集したり別の同期ソフトで複製・同期したりしないでください。

## 初版の制限と注意

- **Nextcloud 34.0.1／34.0.5／35.0.2 + 標準ローカルストレージに、通常のWebDAV方式は使用しないでください。** 同一秒内の変更でETagが再利用される場合があります。34.0.1向けBridgeは別方式です。接続検査はサーバーのすべての挙動を証明するものではありません。
- Bridgeはバージョン依存のNextcloudフックを使用し、34.0.1以外では意図的に停止します。古いセキュリティ保守版を使い続けることを推奨するものではありません。更新先への対応は、そのバージョンでの再検証が必要です。
- 実通信を確認したApacheは`FileETag Digest`を明示した構成です。Apache既定設定では書き込み直後に弱いETagを返し、本プラグインは拒否します。既定構成全般への対応を意味しません。Windows・Android・ownCloudは未検証です。
- Bridge実験版には、対応サーバーが能力を明示した場合に限り、ロック中に計算したSHA-256の版情報をまとめて問い合わせる最適化があります。追跡済みの基準と一致する新鮮なローカル内容、および最後に確認したリモート版が一致すれば、無変更ファイルのリモート本文取得と基準blob読込を省けます。これは**内容のハッシュ計算を省く仕組みではありません**。無変更ファイルでも、端末側の内容全体を読み・ハッシュし、サーバー側でもロック中に内容全体を読み・ハッシュします。変更・未追跡・競合などは保守的な本文読みを続けます。1GiBのローカル・ループバック fixture での比較と、候補のみの10GiB測定結果がありますが、どちらもSQLiteメタデータDBを使った別の測定であり、MariaDBの性能測定ではありません。実Vault・Obsidian GUI・モバイル・WANでの性能測定でもありません。10GiB候補の無変更中央値は約36秒で、既定の同期間隔30秒では大きなVaultの処理に短すぎる場合があります。対象範囲・限界は[性能測定結果](docs/performance-results.md)を参照し、大容量Vaultでは十分に長い間隔で小さなテストVaultから試してください。
- 初期の転送上限は**1ファイル25MiB**、設定可能範囲は1〜100MiBです。上限超過ファイルはスキップとして表示し、削除とはみなしません。大きな添付を必須にする場合は実機で転送方式を追加検証してください。
- Bridgeの上限は1ファイル25MiBです。設定を100MiBにしても増えません。JSON/Base64でバッファするため、ストリーミング転送ではありません。
- ObsidianのネットワークAPIは応答全体をメモリに保持します。HEADと受信後のサイズ確認はありますが、誤ったサイズを返すサーバーや巨大な応答によるメモリ使用を完全には制限できません。ストリーミング転送は未実装です。
- 一覧は最大50,000ファイル／10,000フォルダを目安に制限します。Markdownの自動マージにもサイズ・計算量制限があり、超過時は手動確認に回します。
- バックグラウンドやアプリ終了中の同期は保証しません。新規の定期同期は表示中だけ開始しますが、開始済みのリクエストは即時キャンセルできません。途中で終了した場合は記録から再確認します。
- 独立した外部アプリが無条件にWebDAV上を上書きする行為は防げません。他の同期ソフトや同一ローカルVaultを開く複数プロセスとの同時運用は避けてください。
- Obsidianにはバイナリの原子的な比較更新・条件付き削除APIがないため、別のローカルアプリが書き込み／削除の瞬間に変更する場合の完全な競合防止は保証しません。本文の更新には`Vault.process`／`DataAdapter.process`を利用します。
- シンボリックリンクされたVaultルートや配下は非対応です。デスクトップのパス検証も、別プロセスが検査とI/Oの間に悪意を持ってファイル構造を差し替える攻撃まで原子的には防げません。
- ファイル名の大文字小文字、Unicode正規化、Windows予約名、ファイルとフォルダの衝突を検出した場合は、勝手にリネームせず停止します。改名・移動の履歴追跡はなく、削除＋追加として扱います。
- フォルダは必要に応じて作成しますが、空フォルダだけの同期や不要な空フォルダの自動削除は行いません。
- クラッシュで残った一時ファイル・リモートの孤立した履歴オブジェクトは、誤削除防止のため自動で一括削除しません。
- プラグインの履歴は独立したバックアップサービスの代わりではありません。

## 検証

### 共有前に確認できる限定診断

設定画面の「診断情報を表示」、またはコマンドパレットの「ObsidianCore Sync: 診断情報を表示」から、読み取り専用のJSONプレビューを開けます。JSONのスキーマは`vaultsync-diagnostics-v2`です。バージョン、粗いプラットフォーム、設定の有無・上限、状態の件数、直近の同期／接続確認の要約だけを表示し、URL・アカウント・Vault／ファイル名・本文・認証情報・内容ハッシュ・エラー原文は含めません。件数なども運用情報なので匿名ではありません。確認後のコピーは任意です。自動送信・ファイル保存はせず、コピー拒否時は手動選択できます。

診断のための通信や状態読込は行いません。診断JSONは明示的な`vaultsync-diagnostics-v2`スキーマです。`lastSync.deferred`は保留件数（数値または`null`）で、`outcome`には保留のみで完了した場合の`completed-with-deferred`を使います。中断や実エラーなどの結果は優先され、保留件数は別に残ります。診断には件数だけを出し、ファイル名・生エラー・本文・認証情報は含めません。未読込は`null`、処理中は途中の値です。直近の要約はメモリ上だけに保持し、再起動・停止・設定保存の反映で消えます。`failed`は未変更の保証ではなく、接続確認の`passed`も全構成の安全性保証ではありません。`obsidianApiVersion`は公開API版であり、端末にインストールされたObsidianの版は別途確認してください。

### 端末内の自動同期エラー記録（共有用診断とは別）

設定画面の「自動同期エラーを確認」ボタン、またはコマンドパレットの「ObsidianCore Sync: 自動同期エラーを確認」コマンドから、タイトル「自動同期エラー」の読み取り専用画面を開けます。これは直近1件の自動同期エラーの記録であり、現在の同期状態を読み直したり、エラーの根本原因を断定したりするものではありません。表示・更新では同期を開始せず、通信やディスクI/Oも行いません。

画面には記録時刻（`capturedAt`）、全体の件数要約、所要時間、上限100件のエラー詳細を表示します。詳細にはプライベート情報になり得るパス（マスク／省略される場合を含む）、`context`・`engine`・`recovery-prune`などのフェーズ、診断コード、固定された安全な説明が含まれます。未保存エディターの保留だけはエラーではなく、この記録の作成・置換理由になりません。CAS／HTTP、復旧などその他のエラーには識別可能なコードを表示します。不明なエラーの生の例外文は一切表示しません。診断コードと説明は元のエラー全文や正確な原因を保証せず、この機能だけで断続的なエラーの原因が判明するわけではありません。

自動同期の結果に実エラーが1件以上ある場合、または自動試行がエラーで例外終了した場合だけ、新しい記録を作成します。保留だけの自動試行ではエラートーストを出さず、既存記録も置き換えません。実エラーを含む自動同期結果は、後続の保留のみ／クリーンな自動同期でもRAM上の直近1件として保持します。エラーのない競合・スキップ・中断も既存記録を置き換えません。成功した手動同期も既存記録を消さず、手動同期のエラーも置き換えません。記録はRAM上の直近1件だけで、ファイル保存・自動送信・クリップボードへの書き出しはありません。

「記録を消去」は記録を消し、実行中だった古い試行が後から記録を復活させないための世代境界も設定します。同期そのものや同期状態を変更する操作ではありません。記録は設定保存がコミットされた時点（新しい実行コンテキストの初期化に失敗した場合も含む）、プラグインのアンロード、Obsidian再起動でも消えます。後から設定保存／再起動する予定がある場合は先に記録を確認してください。

この画面のパスはローカル情報です。伏せ字や省略があっても、画面全体やスクリーンショットを共有しないでください。問い合わせ時に必要なら、画面を見ながらフェーズ・診断コード・固定説明だけを手で伝え、ファイル名やパスは省いてください。この記録から不明なエラー原文を取り出すことはできません。既存の「診断情報を表示／コピー」のJSON仕様は変更せず、パス・エラー詳細を含みません。この新しい非公開画面の内容も共有JSONには入りません。

前段階のクライアント機能修正では、改行だけの基準版に対する位置安定な空行マージと、未保存エディター保護ガードの編集保留レポートを修正しました。今回のライセンス・公開準備でも、通常の非空行の3-wayマージ、同期間隔の完了基準方式、同期安全チェック、永続同期状態の版1（`data.json`／`private/`／接続先エンドポイント）は変更していません。プラグインの導入ファイルは引き続き3個です。Bridgeには作者／ライセンスmetadata、SPDXコメント、文書を追加していますが、認証・ロック・CAS・API動作は変更していません。サーバーやMariaDB／Redisをこの作業から変更せず、状態移行・消去も行いません。

前段階の名称変更では、クライアントmanifestの表示名、設定画面・通知・ステータス・コマンド表示、ビルドのバナー、ローカルZIPの名前を更新しました。当時は同期処理や保存先、Bridgeの9実行ファイルを変更していません。単体297件、ビルド／型検査、モバイル模擬スモーク、依存監査（報告された脆弱性0件）が成功しました。模擬アダプターでは旧表示名から新表示名へ切り替えても、同じ接続先・内部IDの基準版／未完了記録と保存バイト列が維持されることを確認しました。`.integration/nextcloud-skH2Tw/result.json`ではMariaDB 12.3.2＋DBロックでBridge 23項目・同期18項目・GUI 13項目を通過し、新表示名・コマンド表示・設定見出しも確認しています。これは今回のライセンス付き成果物やAndroid実機の検証ではなく、当時の履歴です。Bridgeのサーバー表示は既存の`VaultSync Bridge/0.1.0`を維持します。

## 構成

| ファイル | 役割 |
| --- | --- |
| `src/engine.ts` | 同期判定、基準版、条件付き確定、競合、途中処理記録 |
| `src/merge.ts` | 行単位の3-wayマージと競合箇所 |
| `src/webdav.ts` | HTTPS/WebDAV、完全な一覧、強いETag、安全性検査 |
| `src/nextcloud.ts`, `nextcloud/vaultsync_bridge/` | Nextcloud専用の内容ハッシュ・条件付き操作APIとクライアント |
| `src/persistence.ts` | チェックサム付き2スロット状態保存と内容ハッシュ格納 |
| `src/recovery.ts` | ローカル／リモート履歴、保持期限、保護、復元 |
| `src/local.ts`, `src/path-guard.ts` | Obsidianのファイル操作、デスクトップのパス境界検証 |
| `src/policy.ts` | 除外・設定許可リスト・OS間のパス検証 |
| `src/scheduler.ts` | 表示状態とユーザー設定に応じた同期の起動 |
| `src/main.ts`, `src/ui.ts` | Obsidian統合、設定、競合・復元・結果画面 |

マージには`node-diff3`の基準位置付き差分を使用し、globには`picomatch`、DAV XMLには`fast-xml-parser`を使用します。
